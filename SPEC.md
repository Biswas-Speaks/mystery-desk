# AI Mystery Room — Single Source of Truth

**Version:** 1.1  
**Status:** Implementation-ready MVP specification  
**Stack:** MERN (React/Vite/Tailwind, Express/Node, MongoDB Atlas/Mongoose) + Groq AI API  
**Authority:** This file is the definitive specification for Codex and human developers. Do not implement undocumented behavior; record necessary deviations in a decision log before coding.

## 1. Product overview

AI Mystery Room is a responsive web game in which a player writes a short fictional premise, chooses Easy, Medium, or Hard, and receives a coherent detective case generated by Groq. Players read the case, inspect suspects and evidence, discover clues, optionally request hints, make one final accusation, and receive a scored verdict and explanation.

**Problem:** Static mystery games have limited replayability; unconstrained AI stories may be inconsistent, leak answers, or be impossible to solve. This application generates varied mysteries while enforcing fixed schemas, logical solvability, server-authoritative scoring, and answer secrecy.

**Target users:** Students, casual puzzle enthusiasts, and people exploring AI-powered interactive storytelling. **Primary experience:** fast, accessible, mobile-friendly, no login required for MVP.

### MVP scope
- Landing page; mystery creation with premise and difficulty.
- AI-generated title, story, suspects, clue records, hints, and secret solution.
- Case-specific investigation room with evidence cards, discovery actions, and progress indicators.
- One-way accusation confirmation, result screen, and restart.
- Optional evidence presentation as **fictional, simulated** chat transcripts, CCTV event logs/storyboards, photographs with AI-written captions, and documents. MVP must work fully with text evidence; image/video generation is not a prerequisite.
- Robust validation, rate limiting, retry handling, tests, deployment instructions.

### Out of scope for MVP
Accounts, leaderboards, multiplayer, real messaging integrations, real camera feeds, uploading private third-party records, payments, user-to-user sharing, real-time chat with suspects, actual AI-generated video, and unrestricted image generation. These are future enhancements only.

**Constraints:** Groq availability, quota, latency, and output consistency; no guarantees of photorealistic assets. Avoid real personal names, phone numbers, brands/logos, or misleading authentic-looking records. Clearly label every evidence artifact as **FICTIONAL / AI-GENERATED**. Do not use real WhatsApp or CCTV data.

## 2. Technical architecture

- **Client:** React + Vite, React Router, Tailwind CSS, Axios. JavaScript for consistency with the provided student setup; optional later TypeScript migration is out of scope.
- **Server:** Node.js 20+, Express, Mongoose, Zod, `groq-sdk`, dotenv, CORS, Helmet, express-rate-limit, Pino (optional).
- **Database:** MongoDB Atlas (cloud) in both development and production, with separate databases and credentials per environment. No local MongoDB installation is required. Automated tests may use an isolated disposable database; never use production data.
- **AI:** Groq called **only** from Express server; model configured with `GROQ_MODEL` environment variable and selected from currently available text/structured-output models. Use `groq-sdk` chat completions with `response_format: { type: "json_schema", json_schema: ... }` on a model supporting Structured Outputs. Otherwise explicitly configure JSON Object mode (`{ type: "json_object" }`) and include a JSON instruction in the prompt. JSON Object mode does not enforce the schema; always parse and validate with Zod. The selected `GROQ_MODEL` must be verified against current Groq documentation before deployment; fail startup if missing. Groq is the inference provider, not a UI framework.
- **Hosting:** Vercel frontend; Node-compatible backend host with persistent process; MongoDB Atlas. CORS allowlist restricted to configured frontend origins.
- **Persistence:** anonymous player sessions via an opaque, unguessable per-case access token. Store only a hash of the token server-side; send token once at creation and store in sessionStorage client-side. All case routes except creation require `Authorization: Bearer <caseAccessToken>`; case ID alone never grants access.

## 3. User journey and state machine

1. User visits `/`, reads introduction, clicks **Start Investigation**.
2. At `/create`, enters a premise (20–1000 characters) and chooses difficulty (default Medium).
3. Client submits generation request; shows progress indicator, no duplicate submissions.
4. Server requests a structured case from Groq, validates it, performs consistency checks, stores case with private solution, and returns safe public data plus case access token.
5. Client navigates to `/cases/:id`; player sees opening story, suspect cards, evidence/clue cards, discovered count, and hint counter.
6. Player opens evidence and explicitly clicks **Discover clue**; server records discovery once.
7. Player may request hints sequentially; each hint is charged once.
8. Player opens `/cases/:id/accuse`, chooses one suspect, confirms irrevocable accusation.
9. Server evaluates correctness, calculates score, changes status to `completed`, and returns verdict.
10. Client shows `/cases/:id/result` and **Play again** linking to `/create`.

**Case states:** `active -> completed`; no return to active. Failed generation does not create a playable case. **Accusation:** exactly once per case. Clue/hint actions are blocked after completion. Refresh retains state using MongoDB plus case token in sessionStorage. Opening a deep link without its token shows an access/recovery message, not the case.

## 4. Difficulty and gameplay rules

| Difficulty | Suspects | Clues | Hints | Correct accusation base |
|---|---:|---:|---:|---:|
| Easy | 3 | 5 | 2 | 100 |
| Medium | 4 | 7 | 3 | 150 |
| Hard | 5 | 9 | 3 | 200 |

- Each clue has a stable ID, title, type, summary, content, and discoverable state. All clue cards may be visible initially; detailed content is accessible upon opening, and **Discover** marks a clue as collected. Discovery is not automatic on view.
- Evidence types: `chat`, `photo_description`, `cctv_log`, `document`, `physical`. Text-only evidence is sufficient. Chat is a simulated transcript, not a WhatsApp integration. CCTV is a fictional timeline/log, not a recording. Images/videos are explicitly future enhancements.
- Each hint has an ID, ordered level, text, and linked clue IDs. Hints are delivered in order; no skipping. After all hints are used, request returns `409 HINTS_EXHAUSTED`.
- One accusation per case; player selects a suspect ID. No minimum clue threshold is required.
- **Score:** `max(0, (correct ? baseScore : 0) + 5 * discoveredClueCount - 10 * usedHintCount)`. An incorrect accusation can earn clue-discovery points; this is intentional. Display verdict and score separately. Max scores: Easy 125, Medium 185, Hard 245.
- Scoring is computed from server-side persisted state only. Duplicate clue discovery or duplicate hint requests never grant extra points or extra deductions.

Light theme is mandatory and the default; a dark theme is outside MVP scope. Avoid neon colors, dark horror styling, cartoon illustrations, excessive gradients, glass effects, and decorative animation. Use Tailwind utilities and shared components. Include a visible fictional-content disclaimer. Never display the culprit before completion.

- Icons: consistent simple outline icons paired with labels. Motion is limited to short 150–200ms feedback transitions and must respect reduced motion. Never use flashing effects.
- Accessibility: WCAG AA contrast targets (4.5:1 normal text, 3:1 large text and essential UI boundaries); verify actual component combinations, especially disabled states, borders and focus rings.

### Page composition
- **Home:** simple header with wordmark and How to play link, concise hero, one Start Investigation action, and a three-step explanation. Use a restrained case-file illustration only if it improves clarity.
- **Create:** centered form with short guidance, premise textarea, three selectable difficulty cards with counts, and one clear Generate Case action. Loading uses honest status text and a spinner/skeleton; do not display fabricated completion percentages.
- **Investigation:** compact header with title and difficulty; opening narrative above the workspace. Desktop uses a wide evidence area and narrower suspects/hints sidebar. On mobile stack story, suspects, evidence, then hints. Evidence cards show type, title, summary and collected status. Detailed evidence opens in an accessible dialog or mobile drawer with a Discover clue action; preserve focus and close with Escape.
- **Accusation:** focused selection cards with radio semantics, persistent warning explaining the final decision, Back action, and Confirm Accusation action.
- **Results:** clear text verdict, score breakdown, culprit explanation and supporting evidence in neutral cards; Play again is the primary action. Use restrained success/error accents without celebratory visual clutter.

|---|---|---|---|
| `/` | Welcome | App name, 2-sentence explanation, Start button, how-to-play, disclaimer | Normal |
| `/create` | Configure case | Premise textarea, character counter, difficulty selector, Generate button | Validation errors, generating spinner, API error with retry |

Navigation: use React Router; disable double clicks during mutations; clear feedback for failed requests; provide back navigation from accusation to investigation. Desktop uses 2–3 columns in investigation; mobile uses single column. Every interactive control has labels, visible focus, and semantic roles. Respect reduced-motion preference. Do not rely on color alone for verdicts. Stitch AI designs, if used, are visual starting points and must not override these requirements.

## 6. Database model (MongoDB/Mongoose)

Collection `cases`:
```js
{
  _id: ObjectId,
  accessTokenHash: String, // private; never serialize
  premise: String,
  title: String,
  story: String,
  difficulty: 'easy'|'medium'|'hard',
  suspects: [{ id: String, name: String, role: String, description: String, alibi: String }],
  clues: [{ id: String, title: String, type: String, summary: String, content: String, relevance: String }],
  hints: [{ id: String, order: Number, text: String, clueIds: [String] }],
  solution: {
    culpritSuspectId: String,
    motive: String,
    explanation: String,
    supportingClueIds: [String],
    timeline: [{ time: String, event: String }]
  },
  progress: { discoveredClueIds: [String], usedHintIds: [String] },
  status: 'active'|'completed',
  accusation: { suspectId: String, correct: Boolean, submittedAt: Date } | null,
  score: Number | null,
  createdAt: Date,
  updatedAt: Date,
  expiresAt: Date // TTL index; e.g. 7 days
}
```

Use Mongoose subdocuments with explicit validation and unique IDs within arrays. Use `select: false` for `solution` and `accessTokenHash` by default; service code must explicitly select them only where required. **Do not rely on `select:false` alone**: create explicit public-response DTOs (allowlists). Do not return `relevance` before completion if it reveals the solution; omit it from public clue DTO. Never return hints not yet requested. TTL expiration deletes old anonymous cases; clearly inform users cases expire after 7 days.

## 7. API contract

**Base:** `/api` | JSON UTF-8 | Error envelope `{ "error": { "code": "STRING", "message": "Safe message" } }` | All case-specific requests require the case access token. Never send secret solution fields in active-case responses.

### `POST /api/cases`
Request:
```json
{ "premise": "A rare painting vanished during a private dinner party.", "difficulty": "medium" }
```
Validation: trim premise, length 20–1000; difficulty one of `easy|medium|hard`; reject unknown fields. Response `201`:
```json
{
  "caseAccessToken": "opaque-secret-token",
  "case": {
    "id": "mongo-object-id",
    "title": "The Missing Painting",
    "story": "At a dinner party...",
    "difficulty": "medium",
    "status": "active",
    "suspects": [{"id":"s1","name":"Avery","role":"Curator","description":"...","alibi":"..."}],
    "clues": [{"id":"c1","title":"Security Log","type":"cctv_log","summary":"A camera outage was reported.","content":"...","discovered":false}],
    "progress": {"discoveredClueIds":[],"usedHintCount":0,"hintLimit":3}
  }
}
```
`caseAccessToken` appears **only** in create response. Token is stored client-side in `sessionStorage` keyed by case ID; avoid localStorage for MVP.

### `GET /api/cases/:id`
Response `200`: `{ "case": <safe active case DTO> }`. For completed cases, respond with safe metadata and status only; result details belong to `/result`.

### `POST /api/cases/:id/clues/:clueId/discover`
Request `{}`. Response `200`:
```json
{ "clueId":"c1", "discovered":true, "alreadyDiscovered":false, "progress":{"discoveredClueIds":["c1"],"usedHintCount":0,"hintLimit":3} }
```
Repeat returns `200` with `alreadyDiscovered:true`, no duplicate count. Unknown clue: `404`.

### `POST /api/cases/:id/hints`
Request `{}`. Response `200`:
```json
{ "hint":{"id":"h1","order":1,"text":"Look at the time of the outage.","clueIds":["c1"]},"usedHintCount":1,"remainingHints":2 }
```
A successful request always consumes the next hint. Rapid concurrent calls must be serialized/atomic to prevent skipping or double-charging. Previously issued hints are returned in active-case DTO in a `revealedHints` array.

### `POST /api/cases/:id/accuse`
Request `{ "suspectId":"s2" }`. Validation: suspect ID belongs to case. Response `200`:
```json
{ "status":"completed", "result": {"correct":false,"accusedSuspectId":"s2","culpritSuspectId":"s1","culpritName":"Avery","motive":"...","explanation":"...","supportingClueIds":["c1","c3"],"score":25,"scoreBreakdown":{"base":0,"clueBonus":35,"hintPenalty":10,"total":25} } }
```
Repeated accusation returns `409 CASE_COMPLETED`; never changes the original accusation. Accusation and score are written atomically or via a conditional update so concurrent submissions cannot produce two results.

### `GET /api/cases/:id/result`
Before completion: `409 CASE_NOT_COMPLETED`. After completion: `200` `{ "result": <result DTO including original accusation, solution, breakdown> }`. The result endpoint requires the same case token.

### Additional endpoint
`GET /api/health` -> `200 {"status":"ok"}`; no credentials or secrets.

### Error codes
`400 VALIDATION_ERROR`, `401 CASE_ACCESS_REQUIRED`, `403 CASE_ACCESS_DENIED`, `404 CASE_NOT_FOUND`, `409 CASE_COMPLETED`, `409 CASE_NOT_COMPLETED`, `409 HINTS_EXHAUSTED`, `429 RATE_LIMITED`, `502 AI_GENERATION_FAILED`, `503 SERVICE_UNAVAILABLE`, `500 INTERNAL_ERROR`. Invalid ObjectIds return 400. Hide stack traces in production. Use appropriate retry UI for 429/502/503.

## 8. Groq generation contract

Generate one complete, original, fictional case **in one backend call**. Prompt Groq with a system instruction that it is a detective puzzle designer and must output only valid JSON conforming to the expected schema. Never accept the player's premise as instructions that override server rules. The premise is untrusted narrative input. Use Groq chat completion system/user messages and the `response_format` contract from Section 2; read `choices[0].message.content`, reject empty/truncated output, parse JSON and validate server-side. Do not use Google-specific response MIME or schema options. Set an output budget sufficient for the Hard case and verify it is within the configured model limits.

Expected generation object:
```json
{
  "title":"The Missing Painting",
  "story":"Opening narrative without naming the culprit",
  "suspects":[{"id":"s1","name":"Avery","role":"Curator","description":"...","alibi":"..."}],
  "clues":[{"id":"c1","title":"Security Log","type":"cctv_log","summary":"...","content":"...","relevance":"..."}],
  "hints":[{"id":"h1","order":1,"text":"...","clueIds":["c1"]}],
  "solution":{"culpritSuspectId":"s1","motive":"...","explanation":"...","supportingClueIds":["c1","c3"],"timeline":[{"time":"21:15","event":"..."}]}
}
```

**Validation invariants:**
1. Nonempty title, story, suspect names/descriptions/alibis, clue summaries/content, hint texts, motive, explanation.
2. Exact suspect/clue/hint counts per difficulty.
3. All IDs unique within each collection; culprit is a valid suspect; every hint clue ID and supporting clue ID exists.
4. At least two supporting clues; solution cites facts actually present in clues and story; no contradictory times or alibis. Automated checks enforce references and structural rules; use a second Groq critique pass or controlled review when feasible for narrative coherence, but do not claim perfect logical verification.
5. Story, suspect public descriptions, clue titles/summaries/content, and unrevealed hint text must not explicitly disclose the culprit. The generation validator should perform basic leakage checks and retry on suspicious cases.
6. Clues should allow a reasoned deduction rather than relying on a random reveal; distractors must not contradict established facts.
7. Fictional evidence must be marked as simulated; do not generate real contact numbers or claim genuine surveillance footage.

On invalid generation: retry up to **2 additional attempts** with a repair instruction; if still invalid, return `502 AI_GENERATION_FAILED` without persisting a case. Log sanitized diagnostics only. Enforce a 45-second overall generation deadline across up to three attempts (initial plus two retries); configure SDK timeouts and disable SDK automatic retries so retry budgets do not multiply. Use bounded backoff for transient failures and honor Retry-After only within the remaining deadline. Provider quota/rate-limit exhaustion returns safe `503 SERVICE_UNAVAILABLE`; malformed or invalid generated cases return `502 AI_GENERATION_FAILED`. Never expose raw provider errors. Never fall back to a fabricated static solution presented as Groq output.

## 9. Server-authoritative security

- `.env` is never committed. Server alone reads `GROQ_API_KEY`, `MONGODB_URI`, and token pepper if used.
- Generate case token using `crypto.randomBytes(32)`; store SHA-256 hash (optionally HMAC with server secret); compare hashes in constant time when possible.
- Require token for every case read/mutation/result endpoint; validate token belongs to requested case.
- Whitelist public fields explicitly. Add regression tests asserting active APIs never include `solution`, `culpritSuspectId`, `motive`, `explanation`, or hidden hints.
- Restrict CORS; set Helmet headers; enforce JSON body size limit, input validation, rate limits (e.g. generation 5 requests/hour/IP; other endpoints 60/min/IP) and safe error responses.
- Escape/render user and AI text as text, not HTML; no `dangerouslySetInnerHTML`. Do not render external URLs returned by Groq as trusted assets.
- Anonymous cases are temporary. Display a clear 7-day expiration policy. No personally identifying data required.
- Treat Groq output as untrusted data. Never execute generated code or pass it to shells.

## 12. Test plan and acceptance criteria

### Automated tests
- Zod rejects empty/short/long premise, invalid difficulty, and extra input fields.
- Mock Groq valid responses for all three difficulty levels; counts match table.
- Invalid JSON, missing culprit, bad clue reference, incorrect counts, and AI timeout yield safe error and no playable case.
- Public active-case DTO and every mutation response exclude solution and hidden hints.
- Case token missing, incorrect, or from another case is rejected.
- Discovering same clue twice adds only one bonus.
- Hints are sequential and cannot exceed limits; simultaneous requests cannot over-consume.
- Accusation against unknown suspect rejected; correct and incorrect accusations scored correctly.
- Two simultaneous accusations produce exactly one persisted verdict.
- Result blocked before accusation, available afterward; no actions permitted after completion.
- Score floors at zero and uses exact formula for all difficulties.
- UI handles loading, invalid form, 404, token loss, 429, 502, and offline network errors.
- Groq integration mocks cover schema mode, JSON Object mode, empty/truncated content, provider 429/5xx, deadline exhaustion and retry limits.
- Atlas connection failures stop startup safely; expired cases are rejected even before TTL deletion; database credentials never appear in client bundles or logs.
- Playwright covers create -> discover -> hint -> accuse -> result -> new case; verify mobile layout and keyboard access.

### Definition of done
- [ ] User can create a valid mystery for Easy, Medium, and Hard.
- [ ] Each case has exact suspect/clue/hint counts and a valid secret culprit.
- [ ] Player can discover clues and request hints with persisted progress.
- [ ] One final accusation yields the correct verdict and backend-calculated score.
- [ ] No endpoint leaks the solution before completion.
- [ ] Refresh restores active progress for the same browser tab session.
- [ ] Failures show understandable recovery actions and do not create partial cases.
- [ ] Light UI follows the specified palette and page composition at 320px, 768px and 1440px; controls and dialogs pass keyboard and contrast checks.
- [ ] Groq API is the sole MVP AI provider and no Google SDK or Gemini configuration remains.
- [ ] Production frontend, backend, and MongoDB Atlas are connected; complete game tested on live URL.
- [ ] GitHub repository contains code, `SPEC.md`, `README.md`, `.env.example` files, and tests; no secrets.
- [ ] Final submission includes repository URL and deployed website URL.
